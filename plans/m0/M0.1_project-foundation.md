## Objective

Turn the current `project.godot` scaffold into the smallest buildable Warwrought Godot 4.7.1 .NET/C# project using Forward+, with a source-controlled solution/project structure and an ignore policy that keeps generated and local state out of Git. This task establishes prerequisites for a later real `BootstrapLab` scene; it does not create that runtime scene.

## Relevant context

- The repository currently contains `project.godot`, icon assets, repository rules, and planning documents, but no `.sln`, `.csproj`, source tree, export preset, test project, scripts, or production scenes.
- `project.godot` already identifies `Warwrought`, assembly `Warwrought`, and the `Forward Plus` feature. Preserve those locked choices unless empirical validation proves the file is invalid, in which case escalate rather than silently changing renderer or engine configuration.
- The pinned Godot executables are:
  - `D:\Dev\Godot\Godot_v4.7.1\Godot_v4.7.1-stable_mono_win64.exe`
  - `D:\Dev\Godot\Godot_v4.7.1\Godot_v4.7.1-stable_mono_win64_console.exe`
- Command syntax is provisional until M0.4. This task may prove and record candidate invocations, but must not freeze the M0.7 command contract in `AGENTS.md`.

## Required behaviour

1. Verify the pinned Godot paths exist and identify the installed Godot/.NET versions from the actual machine. Record the factual environment information in `docs/environment.md`, including the pinned executable paths and the .NET SDK/runtime information relevant to the project.
2. Establish the production Godot C# project and solution using the `Warwrought` identity:
   - `Warwrought.csproj` is the Godot project’s production C# project;
   - `Warwrought.sln` builds that project from the repository root;
   - target framework and Godot .NET SDK/package integration are compatible with the pinned Godot 4.7.1 .NET editor as demonstrated by a real build;
   - project settings retain Godot 4.7.1/Forward+ and the `Warwrought` assembly name.
3. Set initial desktop window defaults appropriate for development and record them in the Godot project configuration. They need only establish a usable desktop baseline; do not invent final UI/UX requirements.
4. Add a source-controlled `export_presets.cfg` with one candidate Windows Desktop preset compatible with the locked Godot/.NET/C# and Forward+ configuration. This task creates project configuration only; M0.3 proves export and smoke behaviour.
5. Create the initial M0 directories required to support this project configuration: `src/Bootstrap/`, `src/Core/`, `scenes/Labs/`, `tests/`, `scripts/`, `artifacts/`, and `docs/` (with source-controlled placeholder files only where Git needs them). M0.2 completes the full Section 3 source layout without adding speculative implementations.
6. Establish C# namespace and nullable/analyzer conventions appropriate to the actual project. Keep diagnostics useful; do not add analyzer packages or a warnings-as-errors policy merely to enforce cleanliness.
7. Update `.gitignore` so that at minimum Godot caches, .NET `bin/`/`obj/` outputs, export/build outputs, local acceptance artifacts/logs, and local IDE/editor state are not tracked. Preserve any intentional source-controlled placeholder such as `artifacts/.gitkeep` if used.
8. Create `worklog.md` as the factual project handoff record and add an initial entry that identifies this task as in progress/complete only when its acceptance actually succeeds. It must remain concise and not replace task evidence.

## Constraints and invariants

- Build one Godot application, not a general-purpose C# engine or a separate executable game backend.
- Use the pinned Godot 4.7.1 .NET/C# build and Forward+ only. Do not silently use another installed Godot executable, a compatibility renderer, GDScript in place of the required C# foundation, or a different project name.
- Prefer text/source-controlled project state. Do not commit `.godot/`, build outputs, generated project metadata, local logs, export outputs, or machine-specific configuration.
- Do not create `BootstrapLab`, acceptance scripts, test projects, gameplay code, battle primitives, or provisional commands disguised as frozen operational rules in this task.
- If target-framework compatibility, Godot project generation, or a required current C# API cannot be confirmed from the repository and pinned toolchain, stop and provide the exact failed command/output and a concise research request. Do not add compatibility wrappers or guess a permanent solution.

- Confirm the selected .NET SDK/runtime and project target framework are compatible by running the candidate root build command successfully.

- Run `git status --ignored`/equivalent inspection to demonstrate `.godot/`, `bin/`, `obj/`, and local artifacts are ignored rather than staged.

## Acceptance criteria

- The pinned Godot 4.7.1 .NET/C# executable paths and the actual .NET environment are documented factually in `docs/environment.md`.
- `Warwrought.sln` and `Warwrought.csproj` exist, are source controlled, and a real root build succeeds using the selected compatible .NET SDK.
- A clean checkout opens/imports with the pinned Godot 4.7.1 GUI without project/import errors and retains Forward+ and the `Warwrought` identity.
- Initial desktop window defaults and one Windows Desktop export preset are source controlled and retain the locked Godot/.NET/C#/Forward+ configuration. Export execution remains unproven until M0.3.
- The minimal M0 directory structure exists without speculative future-system scaffolding.
- Generated/local state, including `.godot/`, .NET build outputs, and local artifacts, is ignored and not tracked; source placeholders are the only intentionally tracked empty-directory support.
- `worklog.md` records the factual task outcome and candidate command evidence location.
- No production runtime acceptance is claimed yet: that proof remains M0.2.

## Non-goals

- BootstrapLab scene, C# runtime node, JSON report, log scanner, fast tests, successful Windows export, exported-player smoke, or frozen commands.
- M1 battle simulation or any game-system implementation.
- CI, custom runners, wrapper frameworks, dependency injection, ECS, or an architecture framework.

## Escalation conditions

Return to Planner before proceeding if the pinned executables are missing/wrong-version, the installed .NET environment cannot build a Godot-compatible C# project, Forward+ cannot be retained, or a required remedy would alter a locked engine/runtime decision.
