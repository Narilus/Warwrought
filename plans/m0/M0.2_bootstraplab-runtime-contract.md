# M0.2 — BootstrapLab Runtime Contract

- **Status:** Planned — not ready
- **Milestone:** M0 — Project Foundation & Verification Contract
- **Dependencies:** M0.1 accepted with a real Godot C# build
- **Authority:** `/DESIGN.md` §§19–20 and §24; `/plans/implementation_plan.md` §§6 and 9 (M0.2–M0.5); `AGENTS.md`; `godot-project-operations` skill

> This packet becomes normative when Planner marks it **READY**. Builder must not weaken it or substitute a test-only runtime path.

## Objective

Create the smallest maintained production Godot scene, `BootstrapLab`, that runs through a real C# Node, accepts a bounded command-line acceptance scenario, emits a runtime-owned JSON report and explicit log evidence, and exits intentionally in acceptance mode. Establish a small fast .NET test path alongside—not instead of—that production proof.

## Relevant context

- `BootstrapLab` is M0’s real production runtime surface. It is not a fake scene used only by tests and must remain a maintained Godot scene suitable for later bootstrap work.
- Exact command syntax remains provisional. This task proves candidate command shapes; M0.4 alone freezes the exact successful commands into `AGENTS.md`.
- The production C# project is the Godot project. The test project may reference it for pure logic, but cannot become a separate executable/application.

## Required behaviour

1. Create a text `scenes/Labs/BootstrapLab.tscn` and real C# Node/bootstrap code in the production Warwrought project. In ordinary launch mode it displays a minimal visible scene identifying BootstrapLab; in acceptance mode it performs the bounded `bootstrap.m0` scenario.
2. Complete the initial repository layout required by `/plans/implementation_plan.md` §3.1: the named `src/` responsibility folders, `scenes/` categories, `content/` categories, `assets/` categories, `docs/architecture/`, `docs/decisions/`, `docs/milestones/`, `tests/Warwrought.Tests/`, `scripts/`, and `artifacts/`. Use tracked placeholder files only to preserve intentionally empty directories; do not add domain classes, framework code, or fake content merely to populate them.
3. Acceptance mode reads user arguments passed after Godot `--`, writes a JSON report to the explicit caller-supplied path, and exits only after the report write either succeeds or a failure is recorded. The report must be produced by the running Godot scene/node—not fabricated by a shell script.
4. Define one small, versioned BootstrapLab report with at least: schema version, scenario ID, scene identity, Godot version, build/runtime identifier, project version/identity, unexpected-error count, pass/fail, and any failure message/category needed to diagnose a non-pass.
5. Implement the minimal logging/acceptance policy needed for this scene:
   - acceptance invocation uses Godot’s explicit `--log-file` facility;
   - application-caught unexpected failures are counted and reflected in the report;
   - a missing/invalid required acceptance argument or failed report write cannot result in a false pass;
   - log/report inspection is a real verification step, not process-exit-code-only reasoning.
6. Add exactly one transparent report/log verification command or PowerShell helper. It must consume the runtime-produced report and explicit Godot log, return non-success when the report is failed or reports unexpected errors, and return non-success when documented unexpected error/exception/assertion/missing-resource/invalid-node patterns appear in the log—even if Godot itself exits successfully. It must print the detected reason/pattern, cannot create or alter reports/logs, and cannot launch a substitute runtime.
7. Prove the negative path through the real BootstrapLab runtime using a clearly bounded acceptance-only fault-injection scenario/flag. It must produce a failed report and non-success result with diagnosable log evidence, and the verification command must reject it. Normal BootstrapLab and normal `bootstrap.m0` behaviour must not enable this failure path.
8. Add `tests/Warwrought.Tests` using one mainstream `dotnet test` framework. It must reference production code for a small stable-ID equality/order test and any pure report/argument validation that is genuinely useful. Do not mock BootstrapLab and call that production runtime acceptance.
9. Record provisional candidate commands and evidence locations in `worklog.md`; do not alter `AGENTS.md` command policy until M0.4.

## Constraints and invariants

- Use the pinned Godot 4.7.1 .NET/C# console executable for command-line/acceptance work and keep Forward+ project configuration intact.
- Runtime acceptance must directly launch `BootstrapLab.tscn` with the production project and C# assembly. A test-created node, empty substitute scene, standalone test host, or fabricated JSON cannot satisfy it.
- Use Godot-supported direct-scene execution, user args after `--`, `--log-file`, and intentional scene exit. Do not add editor automation, a second runner, a test orchestration framework, or a logging replacement.
- The one transparent report/log verifier required above is the only helper permitted unless direct command invocation demonstrably needs minimal path creation. It must expose the exact Godot command when it invokes one, must not decide pass from anything except actual report/log/process evidence, and must not fabricate output.
- Keep the stable ID deliberately small and local; do not begin deterministic battle RNG, battle models, or M1 primitives.
- Do not treat a passing `dotnet test` result as acceptance of the runtime scene.

## Likely touch points

- `scenes/Labs/BootstrapLab.tscn`
- `src/Bootstrap/` and a small `src/Core/` stable-ID type if needed by the test
- `tests/Warwrought.Tests/`
- `scripts/` only if a transparent helper is demonstrably necessary
- `.gitignore`, `worklog.md`, and ignored `artifacts/` paths

## Expected verification

- Run the production scene directly with the pinned console executable, explicit `--log-file`, a `bootstrap.m0` user argument, and an explicit report location. Inspect the JSON and log, not just exit status.
- Launch the same scene in normal mode through the pinned Godot runtime and confirm its visible BootstrapLab surface exists without runtime errors.
- Run the deliberate acceptance-only failure path and confirm failed report, intentional non-success, diagnostic log output, and non-success from the report/log verifier; then rerun the normal scenario and confirm a clean pass from that verifier.
- Run the candidate `dotnet build` and `dotnet test` commands; tests cover only fast pure logic.
- Inspect the diff and ignored artifact locations to ensure no reports/logs/build outputs are tracked.

## Acceptance criteria

- Direct production launch of `BootstrapLab.tscn` executes `bootstrap.m0`, produces a complete runtime-owned JSON report at the requested path, exits intentionally after it is written, and has no unexpected errors in its explicit Godot log.
- The normal non-acceptance BootstrapLab launch visibly identifies the scene and has no unexpected runtime errors.
- The full initial Section 3 repository layout is present as source-controlled folders/placeholders without speculative domain implementations.
- The deliberately injected acceptance-only failure produces a failed report and diagnosable failure result; it cannot be mistaken for a pass. A subsequent normal acceptance run passes cleanly.
- The one transparent report/log verification path returns non-success for a failed report, non-zero unexpected-error count, or documented unexpected log pattern, including when the Godot process itself exits successfully; it returns success for the clean normal production run.
- A standard `dotnet test` project executes fast stable-ID/pure validation tests that reference production code, while no test result is presented as Godot runtime evidence.
- Candidate build/test/scene command shapes, reports, logs, and their local artifact paths are recorded in `worklog.md` as provisional.
- No standalone application, fake acceptance scene, custom test runner, opaque wrapper, or frozen AGENTS command is introduced.

## Non-goals

- Windows export/exported-player smoke (M0.3).
- Freezing commands (M0.4).
- Battle/campaign/faction gameplay, deterministic combat RNG, BattleLab, or M1 acceptance.
- CI pipelines, test dashboards, log aggregation services, or general logging infrastructure.

## Escalation conditions

Return to Planner if a current Godot 4.7 C# API essential to command-line argument handling, JSON writing, scene exit, or production scene execution is uncertain after repository/skill inspection; if a required direct scene path cannot supply runtime evidence without a new verification architecture; or if the task would require changing the pinned engine/renderer.
