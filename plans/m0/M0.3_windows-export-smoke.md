# M0.3 — Windows Export and Player Smoke

- **Status:** READY
- **Milestone:** M0 — Project Foundation & Verification Contract
- **Dependencies:** M0.2 accepted with clean BootstrapLab scene acceptance
- **Authority:** `/DESIGN.md` §24; `/plans/implementation_plan.md` §§6 and 9 (M0.6); `AGENTS.md`; `godot-project-operations` skill

> This packet becomes normative when Planner marks it **READY**. Builder must not reduce it to editor-only evidence.

## Objective

Add and prove the smallest supported Windows Desktop export path for Warwrought. The exported player must execute the same production `BootstrapLab` acceptance scenario and write its own report/log evidence independently of the Godot editor/scene execution.

## Relevant context

- M0.2 must already prove `BootstrapLab` through the production Godot project.
- Windows desktop is the primary target. Godot 4.7.1 .NET/C# with Forward+ remains locked.
- Export command syntax, preset name, player arguments, and artifact paths remain provisional until M0.4 verifies the full sequence twice.

## Required behaviour

1. Validate the source-controlled `export_presets.cfg` created by M0.1, including its documented Windows Desktop preset, against the locked project configuration. Do not substitute another renderer/engine or synthesize a platform-specific alternative runtime.
2. Document the Godot export-template prerequisite and empirically determine whether templates are installed. If they are absent or mismatched, report a precise environment blocker; do not claim export evidence and do not bypass export with editor execution.
3. Export Warwrought using the pinned console Godot executable and Godot’s supported command-line export flow. Place generated executable/data/log/report artifacts under ignored local `artifacts/` paths.
4. Launch the exported Windows player with the same bounded `bootstrap.m0` acceptance contract used by M0.2. It must accept its required arguments, create a report from the running exported game, create/receive an explicit log, exit intentionally, and pass clean-log inspection.
5. Record provisional export and player-smoke commands, preset name, template prerequisite, outputs, and results in `worklog.md` without freezing them in `AGENTS.md`.

## Constraints and invariants

- Use only `D:\Dev\Godot\Godot_v4.7.1\Godot_v4.7.1-stable_mono_win64_console.exe` for command-line export work.
- The Windows export must run the real compiled Warwrought Godot project and `BootstrapLab`; a copied report, mock executable, or editor-only launch is not evidence.
- Use one committed preset and direct official Godot export. Do not add export wrappers, deployment frameworks, CI configuration, packaging systems, or a second player executable.
- Generated exports, player logs, and acceptance JSON stay ignored. Only the export preset and source/documentation changes belong in Git.
- Do not modify M0.2 report semantics or weaken its failure-path acceptance to make player smoke easier.

## Likely touch points

- `export_presets.cfg`
- `.gitignore` if an ignored export/artifact path still needs coverage
- `worklog.md`
- Existing BootstrapLab argument/report code only for genuine exported-player compatibility fixes

## Expected verification

- Inspect the committed preset and run the pinned Godot official export command to an ignored artifact path.
- Inspect the export log and confirm output executable/data files exist.
- Run the exported player’s `bootstrap.m0` acceptance scenario with explicit report/log locations; inspect both report and log.
- Compare report identity fields to confirm the evidence came from the exported runtime rather than the editor process.
- Run the normal M0.2 production-scene acceptance again if any shared BootstrapLab code changed.

## Acceptance criteria

- A committed Windows Desktop export preset is present and the pinned Godot CLI successfully exports the project to an ignored artifact location.
- The exported Warwrought player runs `bootstrap.m0`, produces a complete passing runtime-owned report and explicit clean log, and exits intentionally.
- The exported report demonstrates exported-player/runtime identity distinct from the editor/scene invocation as applicable to the report design.
- Export template availability/prerequisite and exact provisional commands are documented factually in `worklog.md`.
- No generated export output, report, log, `.godot/` state, or unrelated local file is tracked.
- No editor-only result is used as a substitute for exported-player evidence.

## Non-goals

- Repeating/freezing the complete command contract (M0.4).
- Release distribution, signing, installers, store packaging, CI, or non-Windows exports.
- M1 BattleLab or gameplay implementation.

## Escalation conditions

Return to Planner if required Godot export templates are absent/incompatible, if the pinned engine cannot export the locked configuration, or if satisfying the smoke requirement would require a second runtime, altered renderer, or a new opaque runner. Provide exact command output and inspected log/report paths.
