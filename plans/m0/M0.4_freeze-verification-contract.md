# M0.4 — Freeze and Repeat the Verification Contract

- **Status:** Planned — not ready
- **Milestone:** M0 — Project Foundation & Verification Contract
- **Dependencies:** M0.1, M0.2, and M0.3 accepted
- **Authority:** `/DESIGN.md` §24; `/plans/implementation_plan.md` §§6 and 9 (M0.7 and gate); `AGENTS.md`; `godot-project-operations` skill

> This packet becomes normative when Planner marks it **READY**. Its commands may be frozen only after empirical success; Builder must not change acceptance criteria or replace failures with alternate workflows.

## Objective

Turn the provisional M0 candidates into Warwrought’s small, blessed operational contract by executing the complete build/test/production-scene/export/exported-player sequence from a fresh terminal twice consecutively, inspecting all evidence, and then recording exactly the commands that passed in `AGENTS.md`.

## Relevant context

- M0.1–M0.3 must have already produced real candidate commands and artifact/report formats.
- `AGENTS.md` intentionally states that commands are provisional before M0.7. It must not be updated with a guessed or merely proposed command.
- M0 is complete only with both runtime and exported-player evidence; pure tests and a successful process exit do not suffice.

## Required behaviour

1. Assemble the minimal command sequence using only the successful M0.1–M0.3 candidates, recorded as provisional evidence in `worklog.md` rather than as frozen AGENTS commands:
   - build the Godot C# project/solution;
   - run fast deterministic tests;
   - directly launch production `BootstrapLab.tscn` in `bootstrap.m0` acceptance mode with explicit report/log locations;
   - export the committed Windows Desktop preset with the pinned console Godot executable;
   - run the exported player in the same acceptance mode with separate explicit report/log locations.
2. From a fresh terminal, run the complete sequence twice consecutively without manual editor action. Keep the two runs’ output artifacts separate and inspect each generated report/log before treating the sequence as a pass.
3. Verify every nominal scenario report passes, report identity/scenario is correct, expected files exist, and logs contain no unexpected errors, exceptions, assertions, missing-resource failures, invalid-node/resource failures, or repeated error floods. Run the M0.2 report/log verifier for every report/log pair and require its success. Warnings require factual triage rather than automatic failure.
4. Only after both runs succeed, update `AGENTS.md` with the exact tested commands, pinned executable use, Windows export-template prerequisite, artifact/log locations, and the rule that changes require an explicit infrastructure task with evidence. Preserve AGENTS’ concise operational role.
5. Update `worklog.md` with the two-run results, final command contract location, artifact locations, and any explicitly accepted benign warning (if one exists). Do not commit runtime artifacts/logs unless the repository has deliberately added a versioned fixture/reference artifact.

## Constraints and invariants

- All Godot command-line work uses `D:\Dev\Godot\Godot_v4.7.1\Godot_v4.7.1-stable_mono_win64_console.exe`; no substitute installation, renderer, or engine version is allowed.
- The frozen path must remain direct and boring: standard .NET build/test, Godot direct production-scene execution, Godot command-line export, and exported-player execution. Do not freeze a wrapper stack, custom runner, CI job, IDE macro, or manual editor workflow.
- If an existing candidate fails, preserve the exact command/output, diagnose and repair the actual issue through the existing path, then rerun it. Do not invent a second command simply to obtain a green result.
- Do not weaken report fields, error checks, negative-path coverage, acceptance criteria, or exported-player requirements while freezing commands.
- Generated caches and all runtime/export evidence remain untracked under ignored local paths.

## Likely touch points

- `AGENTS.md`
- `worklog.md`
- Existing `scripts/` only if M0.2 established a single permitted transparent helper
- Ignored `artifacts/` evidence paths

## Expected verification

For **each** of two isolated runs, capture and inspect:

1. Build output and successful exit.
2. Fast test result.
3. BootstrapLab production-scene acceptance report and explicit Godot log, followed by the M0.2 report/log verifier returning success.
4. Godot export output/log and expected player files.
5. Exported-player acceptance report and explicit player log, followed by the same report/log verifier returning success.

The two runs are the evidence required before commands are frozen. After they pass, compare the proposed `AGENTS.md` text against the captured commands character-for-character before saving it.

## Acceptance criteria

- The complete M0 sequence succeeds twice consecutively from fresh terminals without manual editor action.
- Both runs have passing `BootstrapLab` production-scene reports and passing exported-player reports, with expected distinct artifact paths and clean inspected logs.
- The transparent M0.2 report/log verifier returns success for every nominal report/log pair in both runs; its demonstrated failure semantics remain part of the frozen verification path.
- Build and fast tests pass in both runs, but are recorded as supporting evidence rather than substitutes for runtime/export proof.
- The committed Windows export path succeeds in both runs and is followed by a genuine exported-player smoke, not an editor surrogate.
- `AGENTS.md` contains exact, tested commands for build, fast tests, production scene acceptance, Windows export, exported-player smoke, artifact/log locations, pinned executable usage, export-template prerequisite, and the infrastructure-change rule.
- `worklog.md` contains factual completion evidence; no generated/local evidence files are tracked.

## Non-goals

- New gameplay features, M1 work, battle simulation, or broader test coverage.
- CI, automated release pipelines, command aliases that hide the underlying tools, additional verification frameworks, or command redesign for aesthetics.
- Changing locked engine/renderer, acceptance criteria, or the M0 gate.

## Escalation conditions

Return to Planner if any complete-run failure requires a change to the locked engine/runtime decision, if export templates/tooling are unavailable, if logs reveal unresolved unexpected errors, if a candidate command cannot be made repeatable through the blessed tool path, or if commands disagree with what `AGENTS.md` can state concisely and accurately.
