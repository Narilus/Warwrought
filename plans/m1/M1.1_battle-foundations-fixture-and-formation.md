# M1.1 — Battle Foundations, Fixture, and Formation Model

- **Status:** READY
- **Milestone:** M1 — Battle Laboratory: Deterministic Melee Vertical Slice
- **Dependencies:** M0 complete; frozen operations contract in `AGENTS.md`
- **Authority:** `DESIGN.md` §§11, 13, 20, 24–25; `plans/implementation_plan.md` §§3–4, 10 (M1.1–M1.3), 23–24, 29; `deterministic-battle-authority` skill

> This packet is normative. Builder must return to Planner if its objective, required behaviour, acceptance criteria, or non-goals cannot be met without a design decision or a change to the frozen M0 verification contract.

## Objective

Create the smallest deterministic authoritative input boundary for the M1 melee fixture: stable battle/entity identities, versioned deterministic primitives, a validated immutable `BattleDefinition`, and a single rectangular formation layout whose members have stable slots in scaled integer X/Z coordinates.

## Relevant authoritative context

- Every battle must be committed before resolution and contain all inputs required for deterministic outcome. Mutable Godot nodes, camera state, render time, and later content/UI changes cannot mutate it.
- M1 is fixture-only: two basic infantry sides, one advance order, one line formation, basic commander records only if the model requires them, simple melee/morale values, and no final content schema or balance design.
- Formation-first logic is locked. Unit local slot data may exist, but the foundation must not create per-soldier pathfinding/AI or depend on Godot physics/nodes.
- The master plan requires a small explicit deterministic RNG, scaled integer simulation positions, stable loop ordering, and canonical digest input ordering.

## Required behaviour

1. Add focused battle-domain primitives under the existing production project responsibility areas, including stable battle/side/squad/unit IDs as needed, `SimulationVersion`, tick representation, scaled integer horizontal position, deterministic RNG state/API, and a canonical ordered digest writer.
2. Select and document in code comments or the fixture record one M1 scaled-position convention and one starting fixed tick frequency. These are M1 implementation settings, not final game-design constants; all M1 authoritative positions/ranges use the same convention.
3. Define immutable authoritative input records for the narrow fixture: battle identity/version/seed; two sides; squads; member units; deployment/advance data; fixture unit combat/morale values; and the one supported rectangular line formation. Inputs must be safe from externally mutable collection changes after construction/commit.
4. Provide one deterministic fixture factory that constructs a 50–100 unit per side battle which is intentionally capable of producing movement, contact, casualties, morale loss, rout, and a terminal result in later M1 tasks. Fixture values are named/bounded and explicitly not reusable final content definitions.
5. Validate a candidate commitment before simulation. At minimum reject unsupported simulation version, missing/invalid fixture unit references, duplicate battle-side-squad-unit IDs, units assigned to missing squads/sides, invalid member ordering, invalid formation dimensions/slots, and invalid deployment/range values. Return clear validation information; do not silently repair an invalid committed battle.
6. Implement one rectangular rank/file slot generator from formation anchor, facing, width/rank configuration, and deterministically ordered member IDs. Repeated construction must generate the same slot mapping/footprint; it must not depend on dictionary enumeration, scene-tree order, or floating point transforms.

## Architectural constraints and invariants

- Authoritative code must not reference `Node`, scene tree, input, camera, physics, `Vector2`/`Vector3` as stored authoritative state, engine RNG, `System.Random`, timestamps, or frame `delta`.
- Use stable ordered collections for outcome-relevant iteration; maps are lookup aids only.
- The digest writer accepts explicitly ordered primitive authoritative values only. It must not hash JSON text, object serialization, object hash codes, scene files, or memory layout.
- Do not create a generic fixed-point library, general ECS, content registry, command bus, service layer, or generic formation framework. One narrow scaled-position value type and one rectangular layout are sufficient.
- Do not implement simulation ticks, damage, transcript events, battle scene, playback, final result logic, or M2 terrain in this packet.

## Likely integration surfaces

- `src/Core/` for narrow deterministic primitives that are genuinely cross-cutting.
- `src/Battle/Model/` for battle commitment, fixture, validation, and formation model/layout.
- `src/Battle/Simulation/` only for deterministic simulation settings/types if warranted; no loop yet.
- `tests/Warwrought.Tests/` for focused deterministic tests.
- `worklog.md` for the accepted implementation decision/evidence record.

## Required verification

### Pure deterministic tests — required

- known RNG sequence for a fixed seed and expected divergence for a different seed;
- scaled coordinate arithmetic and boundary/invalid-value behaviour;
- stable digest input ordering independent of lookup insertion order;
- immutable commitment/validation rejection cases listed above;
- repeated fixture creation produces identical ordered IDs, formation slots, and canonical input digest.

### Project/runtime regression — required

- Run `dotnet build --nologo` and the existing `dotnet test tests\Warwrought.Tests\Warwrought.Tests.csproj --nologo` path.
- Run the frozen direct `BootstrapLab` regression through the established `AGENTS.md` operational path with explicit ignored artifact/log/report locations, inspect its runtime report/log, and run the existing verifier. This confirms the Godot project remains healthy; it is not M1 gameplay acceptance.

## Acceptance criteria

- All required deterministic tests pass without weakened existing M0 tests.
- A valid M1 fixture commits with deterministic ordered IDs/slots and cannot be mutated through its public construction inputs after commitment.
- Each listed invalid commitment is rejected with an actionable reason rather than entering simulation.
- Same seed/version/fixture inputs generate the same canonical input digest and formation layout; different authoritative seed/input is represented distinctly.
- No authoritative implementation references Godot presentation/physics/RNG/frame timing.
- Build and BootstrapLab regression pass with clean inspected evidence; generated evidence remains ignored.
- `worklog.md` records what was implemented, commands/tests run, and known fixture-only limitations.

## Non-goals

- Fixed-tick battle resolution, contact, attacks, damage, deaths, morale, routing, `BattleResult`, or transcript generation.
- `BattleLab.tscn`, Sprite3D units, visual assets, playback controls, or M1 runtime report.
- Multiple formations/squads per side, doctrine UI, ranged/projectile/ability/commander mechanics, terrain, content registry, campaign, or final balance.

## Escalation conditions

Return to Planner before proceeding if the task needs a final unit-stat schema, final morale formula, final battle tick rate, a general formation taxonomy, a change to the frozen M0 workflow, or a Godot API assumption not already demonstrated and material to the task.
