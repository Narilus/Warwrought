# M1.3 — Production BattleLab Playback

- **Status:** Planned — activate only after M1.2 acceptance
- **Milestone:** M1 — Battle Laboratory: Deterministic Melee Vertical Slice
- **Dependencies:** M1.2 accepted
- **Authority:** `DESIGN.md` §§12, 14–15, 19–20, 24–25; `plans/implementation_plan.md` §§5–6, 10 (M1.9–M1.11), 23–24; `deterministic-battle-authority` and `godot-2p5d-presentation` skills

## Objective

Deliver a maintained production `BattleLab.tscn` that resolves the real M1 fixture once before presentation, creates billboard troop/remains views from its real transcript, plays advance/contact/melee/damage/death/rout/result events, exposes basic playback controls, and emits runtime-owned M1 acceptance evidence.

## Relevant authoritative context

- A watched battle is visualization/playback of an already-determined transcript. Presentation may interpolate, bump, flash, fall, replace with remains, pause, and change speed; it cannot calculate or mutate any battle result.
- M1 needs `Sprite3D` as the troop baseline and minimal symbolic animation. Placeholder art is allowed only if side ownership, damage, death, and remains are visibly distinguishable.
- M1 may use a simple 3D battlefield presentation equivalent. M2 owns deterministic low-poly terrain, height projection, foliage, camera scale, and 500v500 work.
- M0's report/log and direct-scene approach are established. BattleLab must use real production nodes/components, not a test-only substitute.

## Required behaviour

1. Create `scenes/Labs/BattleLab.tscn` as a maintained production scene with visible, inspectable responsibilities equivalent to battlefield root, unit/remains/effects roots, camera, playback controller, and HUD/control surface. Required node/resource absence must fail clearly rather than be silently manufactured by acceptance code.
2. Add a BattleLab C# bootstrap/controller that loads the M1 fixture, validates/commits it, invokes the M1.2 authoritative resolver exactly once before playback, retains its result/transcript, and gives only that data to the playback layer. Normal launch visibly identifies BattleLab; acceptance launch accepts only `battlelab.m1.melee` with explicit `--report` path.
3. Implement a playback clock distinct from fixed simulation ticks. It consumes transcript keyframes/events and supports play-from-start/reset, pause/resume, 1x, and at least 2x playback. Acceptance may drive these controls programmatically to prove their state transitions, but cannot use them to alter authoritative data.
4. Create faction-distinct billboarded `Sprite3D` unit views from the transcript start state. Apply transcript-derived formation/member transforms and visual-only interpolation; show authoritative attack events as short front-rank bumps, damage events as transient red flash, kills as rotation/fall followed by a broad generic remains replacement, and rout as visible withdrawal. Use centralized playback/update ownership rather than independent troop AI/_Process loops.
5. Show a final result state only after the transcript reaches the authoritative battle-ended state. Counter/report values must derive from actual views/events observed by the running production scene, including units spawned, movement/keyframes consumed, attack/damage/death presentation, remains spawned, routed formations shown, control transitions, result shown, authoritative seed/version/digest, and unexpected errors.
6. Reuse and minimally extend the existing transparent `scripts/verify-bootstraplab.ps1` only as needed to verify a specified BattleLab scene/scenario while preserving all existing M0 missing/invalid/failed/unexpected-error semantics. Do not introduce a second verifier, test runner, wrapper, or report fabrication path.

## Architectural constraints and invariants

- The BattleLab production scene is mandatory runtime integration, not an optional shell around a completed C# simulator.
- Playback receives immutable resolution data; it must not call target selection, damage, morale, RNG, or resolution logic. No visual overlap, animation completion, physics, camera, or frame delta can decide outcomes.
- Use `Sprite3D`/normal Node3D baseline and simple placeholder assets where needed. No skeletal animation, animation graphs, NavMesh, rigidbody combat, physics projectiles, per-unit tactical brains, MultiMesh, pooling architecture, procedural terrain, or foliage.
- Keep core M0 acceptance compatibility intact. Do not modify the frozen `AGENTS.md` M0 block; use the same direct pinned Godot CLI shape with a BattleLab scene/scenario and explicit ignored report/log paths.
- The shared verifier must remain transparent and small. It may validate expected scenario/scene and the established core report/log integrity, but BattleLab-specific event/digest checks remain explicit runtime/report assertions rather than a new generic verification platform.

## Likely integration surfaces

- `scenes/Labs/BattleLab.tscn`.
- `src/Battle/Playback/`, `src/Presentation/Battle/`, and a narrow BattleLab scene bootstrap under an existing appropriate namespace.
- Source-controlled placeholder assets under `assets/sprites/` only if necessary for real `Sprite3D` visuals.
- Existing Bootstrap argument/report patterns and `scripts/verify-bootstraplab.ps1`, with compatibility preserved.
- `tests/Warwrought.Tests/` for pure playback mapping/report-argument validation only; scene proof comes from runtime.

## Required verification

### Pure deterministic/supporting tests — required

- playback tick/keyframe interpolation mapping and event dispatch order from a fixed transcript;
- playback controls alter only presentation clock state, not the stored result/digest;
- BattleLab acceptance argument/report validation, including unsupported scenario failure;
- any verifier generalization retains BootstrapLab nominal/negative semantics and accepts the declared BattleLab scenario only when requested.

### Production Godot runtime — required

- Directly launch `res://scenes/Labs/BattleLab.tscn` with the pinned Godot console executable, `--headless`, explicit `--log-file`, `--acceptance=battlelab.m1.melee`, and explicit ignored report path; run the existing transparent verifier against the emitted report/log.
- Inspect report and log. Require runtime-owned `BattleLab` / `battlelab.m1.melee`, `passed=true`, `unexpectedErrors=0`, non-empty authoritative seed/version/digest, and non-zero/expected presentation counters for movement, damage, deaths, remains, rout, and final result.
- Run normal visible BattleLab launch with the pinned GUI executable and verify the actual production scene reaches a readable battle/result surface with visibly distinct sides, movement, contact feedback, damage/death/remains, and rout. Record factual observation/evidence in worklog; do not substitute screenshot-only proof for the report/log.

## Acceptance criteria

- `BattleLab.tscn` directly launches and resolves the M1 fixture once before playback using the M1.2 resolver/result/transcript.
- Runtime creates actual Sprite3D troop/remains views from transcript data and reports observed movement, damage, deaths, remains, routed formation(s), controls, and final result.
- Pause/resume, 1x, and accelerated playback work on the presentation clock without changing stored authoritative result/digest.
- Runtime report identity/scenario, authoritative fields, event counters, `passed=true`, and `unexpectedErrors=0` are valid; direct scene log is clean and transparent verifier succeeds.
- Visible production launch demonstrates the intended minimal symbolic battle language; placeholder visuals remain legible and source controlled if added.
- Pure tests/build, existing BootstrapLab regression, and BattleLab direct runtime acceptance pass; generated evidence remains ignored.
- `worklog.md` records runtime command/evidence, observed presentation behaviour, and M1-vs-M2 visual limitations.

## Non-goals

- Skip/watch equivalence contract, exported-player M1 acceptance, or M1 gate review.
- Procedural low-poly terrain, height sampling, foliage, camera scalability, 500v500, detailed UI/theme/audio/VFX.
- Multiple formations/squads, doctrine, ranged/abilities, final content, campaign/faction systems, replay persistence/scrubbing.

## Escalation conditions

Return to Planner if direct production scene acceptance cannot use the established M0 direct-command/report/log pattern, if the existing verifier cannot be minimally extended without becoming a new framework, if exact Godot 4.7 C# Sprite3D APIs are not demonstrated and must be assumed, or if runtime evidence reveals presentation is deciding outcomes.
