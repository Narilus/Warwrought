# M2.1 — Deterministic Battlefield Data and Height Field

- **Status:** READY
- **Milestone:** M2 — Procedural 2.5D Battlefield & Rendering Scale
- **Dependencies:** M1 accepted; frozen M0 operations contract in `AGENTS.md`
- **Authority:** `DESIGN.md` §§11–14, 20–25; `plans/implementation_plan.md` §§2–6 and 11 (M2.1–M2.4); `godot-2p5d-presentation`, `deterministic-battle-authority`, and `godot-project-operations` skills

> This packet is normative. Builder must return to Planner if its objective, required behaviour, acceptance criteria, or non-goals cannot be met without a design decision or change to the frozen verification contract.

## Objective

Create the small deterministic battlefield-data foundation M2 presentation needs: a validated, seed-driven `BattlefieldDefinition`, deterministic coarse height/terrain-region/deployment data, and one explicit authoritative X/Z height-sampling path. It must be reproducible and inspectable without treating a Godot mesh, physics query, or visual transform as gameplay truth.

## Authoritative context

- M1's committed battle, resolver, transcript, result, canonical digests, and shared skip/watch resolution are accepted contracts. Do not extend or migrate the canonical M1 fixture input merely to attach visual terrain; its accepted input/transcript/result identities must remain unchanged.
- M2 has no terrain combat/movement rule. `BattlefieldDefinition` is explicit deterministic environmental data ready for future authoritative terrain modifiers, while M2 consumes it first for presentation. The M1 resolver must not acquire a visual or Godot dependency.
- Simulation coordinates stay scaled integer X/Z. Rendered elevation is derived: `SimPosition(x,z) → BattlefieldHeightSampler → visual Y`; it is neither a physics surface nor authority for battle motion/contact.
- M2 terrain is a narrow battlefield fixture/profile model, not a province/campaign biome engine or final content schema.

## Required behaviour

1. Add a small immutable `BattlefieldDefinition` under an appropriate existing battle-model responsibility area. It must explicitly identify schema/version, battlefield ID, deterministic seed, horizontal dimensions/bounds, coarse height-field resolution/samples or fully specified generation parameters, terrain-region samples/IDs sufficient for presentation, deployment-zone data, and optional explicit future terrain-modifier samples only where the model genuinely needs them.
2. Provide a deterministic, CPU-only height-field generator with bounded documented inputs: seed, average elevation, roughness, broad hill frequency, and deployment-zone flattening/usable margins. Use an explicit stable algorithm/composition and integer/fixed/scaled data where branch-relevant; do not use GPU noise, Godot RNG/noise, timestamps, `System.Random`, or rendered output.
3. Provide one validated `BattlefieldHeightSampler` (or equivalently narrow model API) that maps bounded authoritative X/Z positions to deterministic height and terrain-region values using a documented interpolation/sample convention. It must define out-of-bounds behaviour clearly and never yield NaN/infinite presentation values.
4. Define at least two fixed M2 battlefield fixture profiles/seeds with observably different but bounded landforms, plus explicit deployment zones that remain usable. They are M2 lab data—not campaign provinces, final biome taxonomy, or M1 combat inputs.
5. Compute an explicit canonical battlefield digest/identity over ordered definition/generation/sample data. Equal inputs must recreate equal data/digest; a stated authoritative seed/profile change must change identity or sampled data as applicable.
6. Keep the relationship to M1 explicit: M2 can select a battlefield profile alongside the unchanged M1 fixture for later presentation, but must not change `BattleDefinition.CanonicalInputDigest`, M1 transcript/result digests, the resolver lifecycle, or M1 verifier expectations.

## Architectural constraints and invariants

- No `Node`, `Node3D`, `MeshInstance3D`, `Vector3` transform, `RayCast3D`, physics body, scene tree, render delta, or engine/GPU noise in deterministic battlefield generation/sampling.
- The definition/sampler is data and narrow queries, not a generic terrain/world framework, service layer, plugin, event bus, spatial engine, or campaign-map abstraction.
- Do not add terrain movement costs/elevation modifiers to M1 combat. If a future mechanic needs them, it must use explicit definition/sampler values and a separately planned authoritative extension.
- Do not generate mesh geometry, scatter foliage, add camera controls, alter troop presentation, create a new acceptance scenario/verifier, or add scale fixtures in this task; M2.2/M2.3 own those integrations.
- Source-controlled plain C# definitions and deterministic fixture construction are sufficient. Do not require final textures, external/generated images, imported noise assets, or a final content registry.

## Likely integration surfaces

- `src/Battle/Model/` for immutable battlefield records/validation and fixture definitions.
- `src/Battle/Simulation/` only if an existing deterministic numeric helper is genuinely reusable; no resolver change.
- `tests/Warwrought.Tests/` for deterministic data/query tests.
- `worklog.md` for factual scope and verification record.

## Required verification

### Pure deterministic C# tests — required

- Same profile/seed/options repeatedly produces equal dimensions, ordered samples/regions/deployments, canonical digest, and representative `HeightAt`/region query values.
- Different declared seed/profile produces a documented terrain identity/sample difference without altering the canonical M1 battle fixture.
- Heights and regions are in documented bounds; corner, edge, interior, and out-of-bounds queries follow documented behaviour; no NaN/infinite conversion enters the presentation-facing result.
- Deployment zones obey the playable/flattened constraints for the fixed profiles.
- Mutation attempts through caller-owned construction collections cannot alter an accepted definition or its digest.
- Existing M1 foundation/resolution/committed-resolution tests preserve the canonical input, transcript, and result digests and same-resolution skip/watch identity.

### Godot project regression — required

- Run `dotnet build --nologo` and the approved full test project.
- Run the existing direct production `BootstrapLab` and `BattleLab` `battlelab.m1.melee` acceptance paths with explicit ignored artifacts/logs/reports and the existing verifier. Inspect both reports/logs; require clean M1 canonical identities and `skipWatchEquivalent=true`/`resolutionIdentityShared=true` for BattleLab.
- This task does not yet claim a terrain presentation runtime proof; M2.2 owns it.

## Acceptance criteria

- Valid M2 battlefield fixtures reproduce deterministic height/region/deployment data and digest from their declared inputs; invalid/bounds-violating definitions fail clearly.
- One tested sampler is the designated future visual-height source from authoritative X/Z; it neither reads a mesh nor exposes physics as authority.
- Fixed deployment zones remain usable and are represented explicitly in data.
- M1's `BattleDefinition` canonical input digest, transcript digest, result digest, sole resolver call, and shared skip/watch resolution remain unchanged.
- Focused/new deterministic tests, full approved tests, build, BootstrapLab regression, and direct M1 BattleLab regression pass with clean inspected evidence; generated evidence remains ignored.
- `worklog.md` records the profiles/seeds, sampling convention, M1 compatibility evidence, and the fact that terrain has no M2 combat effect.

## Non-goals

- Godot terrain mesh/materials/lighting, troop/remains height projection, foliage/prop scatter, camera, BattleScaleLab, or 500v500 measurement.
- Terrain collision/raycasting, NavMesh/A*, terrain physics, obstacle steering, terrain movement costs, elevation combat modifiers, weather, water, final biomes, or province linkage.
- Any M3 combat/doctrine, campaign/faction/AI/content registry, save/replay persistence, final art, ECS/MultiMesh/custom rendering/threading/pooling architecture.

## Escalation conditions

Return to Planner before proceeding if this requires changing accepted M1 canonical identities, adding terrain effects to combat, choosing a final province/biome taxonomy, relying on an unverified Godot API, or treating visual mesh data as authoritative.
