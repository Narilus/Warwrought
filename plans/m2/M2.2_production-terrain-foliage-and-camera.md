# M2.2 — Production Terrain, Foliage, and Camera Integration

- **Status:** Planned — activate only after M2.1 acceptance
- **Milestone:** M2 — Procedural 2.5D Battlefield & Rendering Scale
- **Dependencies:** M2.1 accepted
- **Authority:** `DESIGN.md` §§12–15, 19–20, 22, 24–25; `plans/implementation_plan.md` §§5–6 and 11 (M2.3–M2.6, M2.8–M2.9); `godot-2p5d-presentation`, `deterministic-battle-authority`, and `godot-project-operations` skills

## Objective

Make production BattleLab visibly consume M2.1 battlefield data: generate a faceted low-poly terrain mesh, project troops/remains/effects onto its deterministic height sampler, scatter decorative billboards/placeholder props reproducibly, and provide a readable presentation-only camera. Preserve the real M1 transcript and one-resolution authority boundary.

## Authoritative context

- The M1 `BattleResolution` remains a pre-resolved immutable product. Terrain visuals, camera, foliage, and lighting tell that story; none can affect movement, contact, damage, morale, routing, result, or digests.
- M2.1's definition/sampler—not a rendered mesh collision/raycast—is the sole terrain source for visual Y and terrain presentation choices. Existing M1 fixture data remains canonical and unchanged.
- The intended visual language is Forward+ low-poly 3D terrain with `Sprite3D` troops/foliage and simple props. Placeholder/text-authored assets and primitive meshes are sufficient.

## Required behaviour

1. Add a direct Godot procedural mesh presenter that consumes an M2.1 `BattlefieldDefinition`, builds a consistent coarse grid/topology through a current supported Godot 4.7 C# API such as `SurfaceTool`/`ArrayMesh`, uses sampled heights, generates correct/faceted normals, and assigns restrained region colour/material treatment. The visible topology must reproduce from fixed battlefield data; it must not become a collision requirement.
2. Integrate explicit M2 battlefield profile selection into production BattleLab without modifying the M1 committed battle definition or accepted digests. The maintained scene must validate required terrain/camera roots/resources rather than manufacture substitutes in acceptance code.
3. Replace every flat hard-coded visual Y used for active troops, death/remains, and event effects with the single sampler-based X/Z-to-`Vector3` conversion plus only documented visual offsets. Mesh and sampler must agree at representative grid/interior positions; no per-unit raycast or physics height lookup is permitted.
4. Add deterministic decorative foliage scatter from a documented presentation seed derived from/contained by the battlefield definition. Use bounded count/density/scale/tint/flip variation, billboard tree/bush placeholders, and optional simple primitive rock/landmark props. Keep it readable from the intended camera angle and outside or visually unobtrusive in deployment/contact areas. It has no collision, pathfinding, or authority.
5. Deliver a BattleLab camera rig with pan, zoom, reset-to-battle framing, and bounded optional angle/orbit adjustment only if billboard readability is preserved. Wire normal scene input/control affordances and report/observe the controls through the real production scene. Camera state never reaches authoritative battle code.
6. Retain centralized playback/update ownership. Do not add independent troop `_Process`, scene-tree searches, troop AI, or per-view terrain queries that duplicate the central conversion. Add only restrained M2 zoom/speed readability behavior when directly useful (for example, suppress routine effect creation at high speed/distant framing while retaining death/rout signals).
7. Extend the existing BattleLab runtime report/shared verifier only as minimally required for actual M2 runtime-owned terrain/profile/mesh/foliage/camera evidence. Preserve `bootstrap.m0`, unsupported-scenario failure, M1 negative paths, and all canonical M1 checks; do not make a second report/verifier/runner.

## Architectural constraints and invariants

- Use normal Godot `MeshInstance3D`, `Node3D`, `Sprite3D`, simple materials, and the existing production scene. No MultiMesh, custom render server, bespoke GPU terrain, shader dependency, physics/collision terrain, skeletal animation, or pooling framework.
- Mesh generation is presentation. Data remains authoritative only when a future separately planned simulation mechanic consumes it; M2 adds no combat terrain modifier.
- Do not rerun the resolver or construct an alternate result for a terrain variant. `CommittedBattleResolution` remains the one-resolution boundary and skip/watch still consume its exact retained object.
- Do not replace BattleLab with a test scene or bypass its M1 report/log/acceptance path. A new declared M2 scenario may use the existing direct scene/report/verifier pattern only when needed for fixed-seed terrain evidence.
- Do not add M2.3's 300/500v500 stress data or optimize rendering in this task.

## Likely integration surfaces

- `scenes/Labs/BattleLab.tscn`, current terrain/camera roots, `BattleLab`, and `BattlePlaybackController`.
- A narrow presenter under `src/Presentation/Battle/` and M2.1 model/sampler types under `src/Battle/Model/`.
- Source-controlled placeholder `.tres` textures/materials or procedural primitive meshes under existing assets/content locations only as necessary.
- Existing `BattleLabReport`, Bootstrap exported-player handoff, `scripts/verify-bootstraplab.ps1`, and tests, with M1 compatibility preserved.

## Required verification

### Pure deterministic/supporting tests — required

- Mesh-input/topology mapping and height projection calculations agree with M2.1 sample data at deterministic representative points; presentation code must not need physics/raycast queries to establish Y.
- Fixed foliage scatter inputs reproduce ordered placements/variants and stay inside declared bounds/exclusions.
- Camera/control state and presentation-only readability controls cannot mutate a `BattleResolution`, result digest, transcript digest, or skip/watch identity.
- Existing M1 golden tests still assert the accepted input/transcript/result digests and one retained resolution.

### Actual production Godot runtime — required

- Directly run the maintained BattleLab through the frozen pinned-console/report/log/verifier path for the retained M1 scenario and declared M2 terrain seed/profile scenarios as needed. Inspect runtime-owned terrain/profile/mesh/height-projection/foliage/camera evidence, M1 canonical identities, event counters, `passed=true`, and clean logs.
- Launch the same production BattleLab through the pinned GUI/Forward+ path. Inspect a real visible window at at least two fixed terrain profiles and confirm faceted terrain, distinct billboard formations at sampler-derived elevation, foliage/props, readable lighting, pan/zoom/reset framing, M1 contact/death/remains/rout, and clean normal close/log.
- Run build/full tests and the retained BootstrapLab nominal path; run existing Bootstrap injected-error and unsupported-BattleLab negative checks when modifying report/verifier/Bootstrap routing.

## Acceptance criteria

- Production BattleLab generates repeatable faceted terrain from M2.1 data and visibly uses it instead of the M1 flat ground equivalent.
- Troops, remains, and effects receive Y through the one sampler conversion; deterministic checks and runtime evidence show no mesh/raycast authority.
- Fixed-seed decorative foliage/props reproduce, remain billboard-readable, and introduce no collision/pathfinding/authoritative obstacles.
- Camera pan/zoom/reset works in the production scene and changes no authoritative result/transcript/digest or skip/watch identity.
- Retained M1 direct/runtime proof remains canonical and clean; any M2 report/verifier extension retains nominal and negative M0/M1 semantics.
- Visible Forward+ inspection demonstrates the intended 2.5D environment using source-controlled placeholders/procedural resources; no final art dependency blocks completion.
- Focused/full tests and actual production runtime evidence pass with clean logs; generated artifacts remain ignored and `worklog.md` records factual evidence/limitations.

## Non-goals

- 300v300/500v500 scale harness, performance optimization, MultiMesh, final LOD system, or final frame budget.
- Terrain gameplay modifiers, cover, obstacle collision, water/physics, weather simulation, final biome/content pipeline, province-derived battlefield selection, and campaign map work.
- M3 combat/doctrine, factions/AI, saves/replay persistence, external/generated authored art, audio, or broad UI redesign.

## Escalation conditions

Return to Planner before proceeding if an exact Godot 4.7 C# mesh/camera/Sprite3D API required by the task is not demonstrated or cannot be verified from current documentation, if mesh/sampler disagreement cannot be fixed without raycast authority, if M1 identity changes, or if normal-node profiling already demonstrates an optimization need.
