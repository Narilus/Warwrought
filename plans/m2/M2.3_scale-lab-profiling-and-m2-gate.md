# M2.3 — Scale Lab, Profiling, and M2 Gate

- **Status:** READY
- **Milestone:** M2 — Procedural 2.5D Battlefield & Rendering Scale
- **Dependencies:** M2.1 through M2.2.3 accepted, including the M2.2.3 representative-camera checkpoint `dd86a0d800afa1c9fb95826cbf72a0c928f16927`
- **Authority:** `DESIGN.md` §§14–15, 20, 22–25; `plans/implementation_plan.md` §§2, 5–6, and 11 (M2.7–M2.9 and M2 gate); `godot-2p5d-presentation`, `deterministic-battle-authority`, and `godot-project-operations` skills

## Objective

Provide a production-maintained BattleScaleLab and measured M2 gate evidence for 100v100, 300v300, and 500v500 presentation scale. Establish what ordinary centralized `Sprite3D`/Node3D rendering actually costs before authorizing any rendering-complexity escalation, while proving M1 authority/regressions and a newly exported player remain intact.

## Accepted presentation baseline

- Visible scale profiling uses the accepted production `BattleLab` framing: `Camera3D.position = Vector3(42, 30, 26)`, `rotation_degrees = Vector3(-36, 58, 0)`, orthographic projection, and size `60.0`. It is the representative M2 profiling view, not a declaration of final art direction. Do not create a profiling-only camera that materially reduces visible density or overdraw.
- Existing bounded pan, zoom, and reset behaviour remains part of the measured production presentation. Ordinary troop, foliage, and remains views retain `BaseMaterial3D.BillboardModeEnum.FixedY`; transient hit effects retain full `Enabled` billboarding.
- Scenario labels are exact presentation counts: **100v100** means 100 units per side / 200 presented units total; **300v300** means 300 per side / 600 total; **500v500** means 500 per side / 1,000 total. Runtime evidence must report the requested per-side count, expected total, and actual spawned presentation-unit count separately.

## Authoritative context

- M2 scale concerns rendering/presentation pressure; it must not convert the game into a separate C# renderer or feed presentation state into one authoritative battle resolver.
- The primary 100v100 scale acceptance must exercise an actual committed authoritative resolution and transcript. Deterministic static/synthetic transcripts may isolate 300v300/500v500 presentation construction, but they must be labeled as presentation stress data and must never claim combat authority.
- M2's baseline is the existing centralized playback/update owner with ordinary Godot nodes/Sprite3D. Performance evidence precedes—not follows—MultiMesh, custom rendering, threading, ECS, unsafe code, jobs, or pooling frameworks.

## Required behaviour

1. Add a maintained production `BattleScaleLab` path/declared scenarios through the existing Godot project, report format, transparent verifier, direct scene execution, and exported-player handoff as appropriate. It must use the real M2 terrain/presentation components rather than a detached renderer or test-only substitute.
2. Provide deterministic scale fixtures/scenarios for 100v100, 300v300, and 500v500. The 100v100 scenario commits and resolves a valid real battle through `CommittedBattleResolution`/the sole resolver before playback. Larger presentation-only fixtures, if needed, have explicit ordered static transcript/keyframe data, no RNG/decision logic, clear source identity, and visibly use the same production presentation path.
3. Record runtime-owned metrics separately for headless resolution time where applicable, transcript construction/source classification, scene spawn time, requested/expected/actual presentation-unit counts, active views/nodes/remains/effects, sampled **production Godot playback-frame** durations, aggregate memory available through supported Godot/runtime measurement, playback speed/camera interaction state, and whether the scenario reached its required observation/completion state. The report must state its sample count, measured window, and warm-up exclusion (including an explicit zero when none applies), then report median and p95 frame time from that declared sample set. Report memory source/unit when such measurement is available. Do not fabricate timings in a script or substitute a pure C# benchmark.
4. Exercise the accepted M2.2.3 camera/zoom and normal/accelerated playback during scale observations. At high speed/distant zoom, prove any M2.2 routine-effect suppression remains presentation-only and preserves major death/rout signals in the transcript-driven view.
5. Run a bounded visible 500v500 inspection using the pinned GUI/Forward+ executable. Confirm that all 1,000 views spawn over M2 terrain, the camera can pan/zoom/reset, playback advances under the scripted observation, and normal close/log are clean. Record measured metrics rather than asserting an unmeasured frame-rate claim.
6. Do not implement an optimization tier in response to results. Return a concise bottleneck diagnosis and raw evidence to Planner if median sampled playback time exceeds **33.3 ms**, p95 exceeds **50 ms**, playback/control behaviour is broken, memory is unbounded or clearly pathological, or evidence identifies a rendering/presentation bottleneck. These triggers do not authorize a particular technique. If no trigger occurs, state that the normal-node baseline remains selected; do not add optimization architecture merely to demonstrate ambition.
7. Perform final M2 regression/gate proof through the established direct and exported Windows paths. The exported player must run the exact newly exported executable after same-run output/dependency checks and retain `bootstrap.m0`, M1 BattleLab, M2 scale acceptance, and negative verification behaviour.

## Required verification

### Pure deterministic/supporting tests — required

- Scale fixture/transcript construction repeats with stable ordered IDs/keyframes and clearly distinguishes real-resolver versus synthetic presentation sources.
- The 100v100 fixture uses a committed definition and one retained authoritative resolution; playback/control/camera/effect-detail settings do not change its result/transcript/digests.
- Metric aggregation/window calculation and report validation reject missing/invalid/negative/inconsistent values without inventing a second benchmark runner.
- Existing M1 deterministic tests retain all canonical digests, skip/watch same-reference/equality, and playback-only invariants.

### Production Godot and profiling proof — required

- Run direct pinned-console M2 scale scenarios with explicit reports/logs and the existing verifier; inspect runtime-owned 100/300/500 counts, source identity, timing/metric samples, terrain/profile identity, playback/camera state, pass/zero-error state, and clean logs.
- Run pinned GUI production scale inspection, including the 500v500 scenario, and record the visible scene/camera/control/completion observation with its explicit log. Headless success is not a substitute.
- Run direct BootstrapLab and canonical M1 BattleLab nominal acceptance/verifier. Re-run injected Bootstrap failure and unsupported BattleLab/M2 scenario rejection after any verifier or Bootstrap routing change.
- Use the frozen fresh-root export/player procedure with the pinned templates. Verify same-run executable/PCK/managed files, launch the exact exported executable using `Start-Process -PassThru -Wait`, then inspect/verifiy finalized M2 scale and canonical M1 BattleLab report/log evidence.

## Acceptance criteria

- Production M2 scale path visibly and deterministically constructs M2 terrain plus 100v100, 300v300, and 500v500 presentations; the 100v100 path uses the real authoritative resolver and larger synthetic sources, if used, are explicitly reported as non-authoritative presentation stress data.
- Runtime-owned reports record the defined scale/source/count/timing/warm-up/memory/control/completion/error fields rather than guesses; 500v500 spawns 1,000 views at the accepted production framing, camera controls operate, playback advances through the required observation, and no runtime error/flood/missing node/resource occurs.
- GUI/Forward+ observation and direct acceptance prove actual production rendering; an exported Windows player independently proves the accepted M2 path using the newly exported executable.
- M2 performance evidence is assessed against the README escalation triggers. No disallowed optimization tier is introduced; any triggered condition is reported to Planner with raw metrics rather than repaired through speculative architecture.
- The protected M2.1/M2.2 identities and M1 input/transcript/result identities above remain exact; ordinary BattleLab still proves same retained resolution identity and skip/watch equivalence, and ScaleLab scenarios do not alter authoritative M1 results.
- Bootstrap nominal/injected-negative, unsupported scenario, M1 BattleLab, tests/build, direct runtime, exported player, reports, and logs all retain their protected semantics and pass where nominal.
- `worklog.md` records exact scenario identities, source classifications, metrics, observed GUI behaviour, export/player evidence, escalation conclusion, and M2 limitations.

- M3 multi-squad/doctrine/ranged/abilities/terrain gameplay, campaign/province linkage, faction/content/AI systems, saves/replay persistence, final art/audio/VFX, CI, or packaging cleanup unrelated to M2.

## Escalation conditions

Return to Planner if normal-node evidence crosses an M2 README escalation trigger, if a 100v100 authoritative fixture cannot be expressed without modifying accepted M1 identities, if the real scale scene cannot share production terrain/presentation components, if exported-player acceptance needs a new operational workflow, or if any proposed repair would introduce a prohibited optimization or later-milestone feature.
